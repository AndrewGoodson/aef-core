# Combined Reference & Build Guide: Self-Improving Agent “Mind Graph” + Fleet Ops Dashboard (One Offline HTML File)

## TL;DR

- **Build the artifact as a two-stage system**: an offline generation pipeline (Python or Node — unconstrained) that bakes force-layout coordinates, history, and timestamps into an embedded `<script type="application/json">` block, and a delivered single HTML file that reads only that block. On the persistence dispute, **Report B wins**: bake coordinates at generation time; do not use localStorage or a fresh runtime layout.
- **Renderer verdict: hand-write a d3-force + Canvas painter, inlining only d3-force (~8.3 KB min).** Cytoscape.js (UMD 365,007 bytes min / 112,477 bytes gzip, per its own `.size-snapshot.json`) and sigma.js+graphology (~160 KB min combined, plus a build step) are technically inlinable but heavyweight and default to healthy-looking circles — the opposite of the “unknown is loud” requirement. For the dashboard, inline **uPlot (~45 KB min, MIT)** for sparklines/control-charts/state-timelines and hand-draw the Sankey/CONSORT flow.
- **The two reports agree on the load-bearing decisions** (Cytoscape as the reference grammar, coordinate persistence, “No Data” as a first-class non-green state, width=cumulative vs brightness=recency as separable channels, mid-edge gate glyph, animation-as-exception, charcoal ground, dead-man’s-switch/registry-left-join, no decorative glow, error-type-and-rate-only drill-down, and “everything looks healthy” as the cardinal failure). Where they diverge (funnel vs CONSORT, diamond vs rectangle gate, halo vs birth-flag, health-ring vs instrumentation-border), **Report B’s more conservative, absence-first choices should win in six of seven cases.**

## Section 3 — Adjudicated Disagreements

|#|Dispute              |Report A                                   |Report B                                             |**Verdict**                                         |
|-|---------------------|-------------------------------------------|-----------------------------------------------------|----------------------------------------------------|
|a|Layout persistence   |localStorage / runtime layout option       |Bake coordinates into artifact at generation time    |**B**                                               |
|b|Hero dashboard visual|Funnel (rejection = healthy)               |CONSORT-style cohort flow, neutral rejection branches|**B**                                               |
|c|Gate glyph           |Mid-edge diamond                           |Mid-edge rectangle `──[H]──`                         |**B**                                               |
|d|New-node treatment   |Decaying halo fade (age = now − first_seen)|Static birth-flag tab (“NEW”/“3h”/“2d”)              |**B (primary), A (secondary)**                      |
|e|Node border          |Health ring (Datadog-style)                |Instrumentation-quality only; health in fill         |**B**                                               |
|f|Theme                |Single dark theme                          |Dual themes via prefers-color-scheme                 |**B**                                               |
|g|Small-multiples role |Scrubber + ghost primary                   |Difference-map primary + two synced panes            |**Split: B for “what changed”, A’s scrubber opt-in**|

**(a) Persistence — Verdict: Report B.** The hard constraint is *read-only, no writes, no requests, renders offline*. localStorage is a write to browser storage and makes the view stateful/non-reproducible; a fresh runtime force layout means the same data renders differently each open, destroying the spatial-memory requirement. B’s approach — carry previous coordinates forward, place new nodes offline via deterministic seeding (weighted centroid of positioned neighbors; perimeter placement by hash of stable ID, never `Math.random`), run bounded relaxation with a hard displacement budget (~1 node diameter per version), store previous_x/previous_y + layout_reason — satisfies persistence, reproducibility, and read-only simultaneously. *Overturned if*: the delivered file were ever allowed to be interactive-stateful (it isn’t).

**(b) Hero visual — Verdict: Report B.** A funnel’s visual grammar implies “wider top = success, leakage = loss,” which is actively wrong here: a rejected proposal is the gate *working*. CONSORT’s grammar treats every exclusion as an expected, counted, reason-annotated branch — a precise semantic match for proposed→(static-rejected | behavioral-rejected | human-rejected | escalated | merged→(durable | rolled-back)). Use NEUTRAL colors for expected rejection branches; reserve red for operationally abnormal events. *Overturned if*: user testing shows operators misread the CONSORT branches as errors — but that’s fixable with labeling, whereas the funnel’s “leakage = bad” implication is structural.

**(c) Gate glyph — Verdict: Report B.** A diamond is the flowchart symbol for a *decision/branch* — it implies conditional logic the gate doesn’t perform. The gate is an accountable checkpoint that a proposal passes through, so a rectangle interrupting the edge (`──[H…]──` awaiting, `[H✓]` approved, `[H✗]` rejected, `[H!]` escalated, `[H↶]` rolled back) reads correctly and, per B, lets you collapse parallel policy-identical edges into one cluster-boundary gate. *Overturned if*: the system actually has branching approval logic (multiple exclusive downstream paths chosen by the gate), in which case a diamond regains meaning.

**(d) New-node treatment — Verdict: Report B primary, A’s halo as an opt-in.** B’s objection is decisive: a pulsing/fading halo is (1) confusable with an alarm, (2) invisible in screenshots, and (3) implies live motion in a static file. A static birth-flag tab (“NEW”, “3h”, “2d”) computed from `now − first_seen_at` against the embedded `generated_at` is deterministic, screenshot-stable, and encodes a real quantity. Keep A’s one-time entrance animation ONLY when the user explicitly navigates time. *Overturned if*: reduced-motion-safe, non-looping halos test better for drawing the eye — but the tab still must remain the source of truth.

**(e) Node border — Verdict: Report B.** This is the subtlest and most important call. If the border encodes health (Datadog), then an uninstrumented node with no data still gets *some* border treatment and risks looking fine — violating “a node with no data must not look healthy.” B’s split — **fill = measured operational state; border = evidence/instrumentation quality** (solid=fresh full coverage, segmented=partial, broken+”?”=none, double+timestamp=newly instrumented) — makes “we have no evidence” a distinct, visible construction. Health and trust-in-the-measurement are genuinely orthogonal, so they deserve separate channels. *Overturned if*: user testing shows two border/fill semantics overload the operator — then fall back to A’s ring but with an explicit hatched “unknown” ring that is visually louder than any health color.

**(f) Theme — Verdict: Report B.** B cites the honest finding that neither polarity is universally superior (individual differences). Authoring both themes via `prefers-color-scheme` with *identical semantic ordering* (never auto-invert luminance meaning) costs little and respects the operator’s environment (wall display vs desk). *Overturned if*: an on-hardware task test shows one polarity clearly wins for the abandoned-path and missing-node tasks on the target display — then ship that one and drop the maintenance cost.

**(g) Small multiples — Verdict: Split.** For the specific task “what changed between two wiring versions,” B’s difference-map mode (two synced “then”/“now” panes + a union-diff view) is the better primary surface: in the Archambault/Purchase/Pinaud GD 2010 study, *“difference maps produced significantly fewer errors when determining the number of edges inserted or removed from a graph as it evolves over time. Also, difference maps were significantly preferred on all  tasks.”*   A’s timeline scrubber with ghost mode is valuable but should be a secondary, explicitly user-initiated mode (staged GraphDiaries-style transitions), because animation is worse for change-counting and can’t be screenshotted. *Overturned if*: operators mostly ask “show me the trajectory over many versions” rather than “diff these two” — then the scrubber earns primary status.

## Section 4 — Unified Encoding & Dashboard Spec

### 4.1 Mind-Graph Encoding Contract (node channels)

Enforce a hard rule: **no visual property renders unless its backing field is non-null; a null health field forces the UNKNOWN construction.**

- **Position (x, y):** structural identity — baked offline, persistent, carried forward across layout versions with a displacement budget of ~1 node diameter/version. Encodes nothing but identity/memory.
- **Radius:** `min + k × sqrt(log1p(lifetime_execution_count))`, capped; caps printed in legend. (Area is less accurate than position/length per Cleveland & McGill, so keep the transform gentle and never use area for composition balance.)
- **Fill:** measured operational state ONLY — normal / degraded / failed / pending. No multi-hue role palette.
- **Border (reserved exclusively for evidence/instrumentation quality):** solid = fresh full coverage; segmented = partial coverage; broken + “?” = none; double + timestamp = newly instrumented.
- **Interior glyph:** node kind (agent / gate / terminal) — role lives *inside* the circle, because variable outlines break edge attachment and hit-testing.
- **Shape:** circles only.
- **Birth flag:** static tab (“NEW”/“3h”/“2d”) from `now − first_seen_at`.
- **Preattentive budget:** ≤3 variables (size, fill+icon, border pattern). **No glow, ever** — use a crisp concentric ring if an outer treatment is needed.

### 4.2 Two-Layer Edge Model + Four-State Dead/Never Taxonomy

- **History rail (outer stroke):** width = `log1p(lifetime_traversal_count)` — monotonic, never decays.
- **Activity core (narrow inner stroke):** luminance = `time_since_last_traversal` (recency, decays); optional continuity = recent rate.
- **The four (really five) endpoint states — “dead” is NEVER inferred from inactivity alone:**
1. **Never observed** (configured + valid telemetry + zero count): hairline **dashed**, open endpoint markers.
1. **Dormant** (count > 0, none in window): solid rail, dim/absent core.
1. **Retired** (explicit retired_at/disabled_at): dim rail ending in a perpendicular terminal cap.
1. **Unknown** (coverage absent/invalid): alternating patterned edge, midpoint “?”, makes NO zero-count claim.
1. (**Stale**: dominant stale treatment; last-known state only in a small inset.)
- This directly satisfies the user’s requirement: **heavily-used-then-abandoned = thick history rail + dim/dark core (state 2); never-taken = thin dashed hairline (state 1)** — unmistakably different.
- **Gate:** rectangle interrupting the edge; states `[H…] [H✓] [H✗] [H!] [H↶]`; collapse policy-identical parallel edges into one cluster-boundary gate.
- **Legend requirement:** concrete worked examples with windows and numbers (“10 traversals / 2 min ago”, “10,000 / 90 days ago”, “0 observed”); print every log/sqrt transform and cap. Never a bare “brighter = more active.”

### 4.3 Timestamps / Staleness Self-Display

Embed `generated_at`, `data_through`, and the expected reporting interval in the JSON block. Compute all visible ages from those embedded values so a file opened 3 days later *looks* 3 days stale. **No “LIVE” label ever** on a static file.

### 4.4 Dashboard Spec (above-the-fold order)

1. **Coverage + freshness strip** — answers “can I trust the rest of this page?” Header reads e.g. “Reporting fresh 87/100 · Stale 8 · Never instrumented 3 · Telemetry error 2 · Oldest expected report 19h42m.” Build the fleet list from an authoritative REGISTRY and LEFT-JOIN telemetry into it — never assemble it from whoever emitted data.
1. **Exception queue** — rollbacks, gate-eval errors, stale reporting, long-pending human decisions, abnormal collapse/surge, repeated proposal loops, yield degradation. NOT ordinary rejections.
1. **Rolling cohort flow (CONSORT-style)** — branches with count, % of cohort, comparison to own historical expected range, median + p-high time-in-stage, top structured rejection categories, and a missing-classification count. ≤6 top-level outcomes. Neutral colors for expected rejection branches; red only for operationally abnormal.
1. **Process-stability band beneath the flow** — control-chart / Shewhart expected-band treatment on proposal arrival rate, per-stage rejection rate, escalation rate, human decision latency, rollback-adjusted durable-merge yield, telemetry freshness/coverage, gate eval duration/timeouts. Per-repo or peer-group baselines. **90% rejection is healthy if the band is 88–93%; a sudden 55% means the gate stopped; 99.9% means the generator broke.**
1. **Fleet table/lanes** — one row per registry repo, each with a tiny Grafana-style state-timeline (duration as length) and a freshness rail (normal / amber clock + age / hatched unknown pinned to top / broken outline “NEVER REPORTED” with no score / collection-error distinct from no-data). Stale repos float to the TOP; time-since-last-report is a first-class climbing number. Never retain a last green fill as dominant after reporting stops.

### 4.5 Loop-vs-Human Comparison (label OBSERVATIONAL)

Primary metric: **durable changes per human review hour** (durable = merged + post-merge checks passing + not rolled back within window). Supporting: median time from need→durable change, rollback/rework rate, human minutes per durable change, post-change incident rate. Cite DORA framing (throughput balanced with change-fail rate). **Label the comparison OBSERVATIONAL / adjusted-association unless randomized or matched on repo, size, subsystem, and risk** — and if the direct-human-edit counterfactual isn’t stored, say so on the panel.

## Section 6 — Build Plan (staged, with decision thresholds)

**Stage 0 — Encoding contract first (before any rendering).** Write the contract as code: a validator that refuses to emit a visual property when its backing field is null and forces the UNKNOWN construction (hatched interior, broken border, “?”). Threshold: 100% of node/edge visual properties must have a named backing field or the build fails.

**Stage 1 — Generation pipeline.** Derive the traversal graph (optionally with pm4py DFG discovery), compute layout OFFLINE with graphology-layout-forceatlas2 + noverlap (or NetworkX), using deterministic seeding (weighted centroid of positioned neighbors; perimeter by hash of stable ID; never `Math.random`). Carry previous_x/previous_y forward; run bounded relaxation with a **hard displacement budget of ~1 node diameter per layout version**; store layout_reason. Embed graph + positions + history + `generated_at` + `data_through` + expected interval in a `<script type="application/json">` block.

**Stage 2 — Renderer choice (now decidable with verified sizes).** **Hand-write a Canvas renderer driven by inlined d3-force (8.3 KB).** Decision thresholds: (i) if hand-rolling the two-layer edge + four-state taxonomy + hit-testing exceeds your effort budget, fall back to **Cytoscape.js** (365 KB min / 112 KB gz) with a fully overridden stylesheet — acceptable because it’s genuinely inlinable; (ii) escalate to **sigma.js+graphology** (~160 KB min + build step) ONLY if a single view must render **> ~2,000 simultaneously visible nodes/edges** at interactive frame rates — below that, Canvas is fine and avoids WebGL glow.

**Stage 3 — Persistence + new-node channel.** Verify a file reopened later renders pixel-identical node positions and shows correct staleness/birth-flag ages computed from embedded timestamps. Threshold: zero coordinate drift between two opens of the same artifact.

**Stage 4 — Dashboard around absence.** Build the registry left-join first (coverage/freshness strip), then the exception queue, then the CONSORT cohort flow with Shewhart expected-bands, then the fleet table with state-timelines (uPlot). Threshold: a repo that stops reporting must move UP and change construction within one generation cycle; a synthetic “silent repo” test must never render green/blank.

**Stage 5 — Three temporal modes.** (1) default accumulated present; (2) two-date difference-map (primary “what changed”, two synced panes); (3) opt-in scrubber with staged transitions on explicit user action. Respect `prefers-reduced-motion`; all static end-states must be fully interpretable.

**Stage 6 — Two operator task-tests on target hardware.**

- **Polarity A/B:** ship both themes via `prefers-color-scheme`; test light vs dark on the actual wall display / desk monitor for the “find the abandoned path” and “find the missing-reporting node” tasks. Threshold to drop a theme: one polarity yields materially lower error/time on both tasks.
- **Comparison mode A/B:** difference-map vs two-pane vs scrubber, measured on “find abandoned path / find missing-reporting node / compare wiring versions / trace a gate.” Choose the mode that minimizes **error rate and time**, not the one with the highest FPS. Threshold: promote the scrubber to primary only if operators’ dominant question is trajectory-over-many-versions rather than diff-these-two.

## What I am least sure about

1. **Exact inlined footprint of vasturiano/force-graph.** I verified d3-force (8.3 KB min), Cytoscape (365 KB min / 112 KB gz from its own size-snapshot), sigma (~94 KB), and graphology (~67.5 KB), but the force-graph UMD min size resisted verification (bundlephobia renders numbers client-side; the dist listing didn’t return a byte count). This doesn’t change the verdict (hand-write + d3-force), but a firm number would let me rank force-graph precisely against Cytoscape. *Settled by*: fetching `app.unpkg.com/force-graph@1.51.4/files/dist` in a browser or reading the raw dist file’s byte length.
1. **The single best contrast polarity and the max useful graph density before aggregation.** Both are genuinely empirical and hardware-dependent (both reports flag them). *Settled by*: the Stage-6 on-hardware task tests measuring operator error/time for the abandoned-path and missing-node tasks across polarities and node counts — the threshold is where error/time rises, not where FPS drops.
1. **Whether the loop-vs-human comparison can ever be causal.** Until proposals are randomized or matched on repo/size/subsystem/risk, “durable changes per human review hour” is an adjusted association, not a causal claim. *Settled by*: a stepped-wedge or matched-cohort design; until then the panel must be labeled OBSERVATIONAL and disclose when the direct-human-edit counterfactual isn’t stored.
